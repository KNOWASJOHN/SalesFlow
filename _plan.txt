Signaling Module 1: Protocol &amp; Message Contract
Depends on: Completed backend Modules 1-8 (existing FastAPI app, database).
Files touched:
app/signaling/protocol.py
app/signaling/models.py
app/signaling/exceptions.py
Build scope:
Define the message envelope as a Pydantic model: type, call_id, interaction_id, sender, target, payload, timestamp.
type is a fixed enum: offer, answer, ice_candidate, join, ready, call_state, hangup, error.
payload stays a free-form dict (SDP/ICE data varies by message type) â€” do not over-validate its internal shape yet.
Define custom exceptions: InvalidMessage, UnauthorizedPeer, RoomFull, RoomNotFound.
Write a validate_message(raw_json) function that parses and returns a typed envelope, or raises InvalidMessage.
Do NOT build the WebSocket route, room logic, or manager yet â€” this module is the contract only.
Done when:
A standalone script/test can call validate_message() with a valid offer JSON and get back a typed object.
Passing malformed JSON or an unknown type value raises InvalidMessage, not an unhandled exception.
The exact message shape matches Section 3.2 of the WebRTC doc exactly (this is the contract other teams build against â€” do not diverge from it).
Signaling Module 2: Room &amp; Peer Registry
Depends on: Module 1.
Files touched:
app/signaling/room.py
Build scope:
Define a Room class: room_id (format call:&lt;call_id&gt;), holds at most one customer peer and one employee peer.
Define a Peer representation: peer_id, role (customer/employee), the live WebSocket connection object.
Room methods: add_peer() (raises RoomFull if the role slot is already taken), remove_peer(), get_other_peer(), is_ready() (both slots filled).
This module holds pure in-memory logic â€” no WebSocket or FastAPI imports here. Keep it testable in isolation.
Done when:
A unit test can create a Room, add a customer peer, add an employee peer, and get_other_peer() from each side returns the correct counterpart.
Adding a third peer (e.g. a second customer) raises RoomFull.
Removing a peer correctly frees that role&apos;s slot so a replacement could join if that&apos;s ever needed.
Signaling Module 3: Signaling Manager
Depends on: Modules 1-2.
Files touched:
app/signaling/manager.py
Build scope:
SignalingManager holds the registry of all active rooms (dict of call_id -&gt; Room).
register_peer(call_id, peer_id, role, websocket) â€” creates the room if it doesn&apos;t exist, adds the peer.
send_to_peer(call_id, sender, payload) â€” looks up the room, finds the other peer, forwards the message over their WebSocket. Raises RoomNotFound if the room doesn&apos;t exist.
close_room(call_id) â€” notifies any remaining peer, then removes the room entirely.
remove_peer(call_id, peer_id) â€” for disconnect cleanup; must be idempotent (safe to call twice without error).
Do not persist any of this to PostgreSQL â€” this is explicitly ephemeral, in-memory state per the WebRTC doc.
Done when:
A test can simulate two fake peers joining the same call_id, call send_to_peer from one, and confirm the manager attempts delivery to exactly the other peer.
Calling remove_peer twice for the same peer does not raise an error.
send_to_peer for a call_id with no such room raises RoomNotFound rather than crashing.
Signaling Module 4: WebSocket Endpoint
Depends on: Modules 1-3.
Files touched:
app/api/websocket_signaling.py
app/main.py (register the route)
Build scope:
Implement WS /ws/signaling per the flow in Section 4.3 of the WebRTC doc: accept socket, authenticate, receive join message, register with SignalingManager, then loop receiving/validating/routing messages.
On the join message, register_peer() with the manager; on offer/answer/ice_candidate, call send_to_peer(); on hangup, forward it then close_room().
Wrap the main loop so any disconnect (explicit or abrupt) triggers remove_peer() in a finally block â€” this must run even if the client vanishes without sending hangup.
Override sender in every outgoing envelope with the authenticated socket&apos;s own peer_id â€” never trust a client-supplied sender.
For this first pass, authentication can reuse whatever simple identity the REST API already assumes (no need to build a new auth system) â€” just make sure the socket knows which peer_id/role it represents before anything else happens.
Done when:
Two separate WebSocket clients (e.g. two browser tabs or two simple test scripts) can connect, join the same call_id with different roles, and messages sent by one arrive at the other.
Closing one client&apos;s connection (killing the tab/script) causes the manager to clean up that peer without crashing the server or leaving the room in a broken state.
Sending a message with an invalid type or malformed JSON gets a clean error response, not a server crash.
Signaling Module 5: Interaction Ownership Validation
Depends on: Module 4, existing Modules 1-8 (journeys/interactions tables and endpoints).
Files touched:
app/signaling/manager.py (extend)
app/api/websocket_signaling.py (extend)
Build scope:
Before allowing a join to succeed, verify the interaction_id in the message actually exists (query the interactions table) and that the joining peer is plausibly allowed in that call (e.g. the employee_id on the interaction matches an employee peer, matching customer via the journey).
Reject SDP/ICE messages if the sender has not first completed a valid join for that call_id.
Only ever route messages to a peer in the same call room â€” never allow cross-room delivery even if call_id is guessed or reused.
Done when:
Joining with a interaction_id that doesn&apos;t exist in the database is rejected with a clean error, not silently accepted.
An offer/ice_candidate sent before a successful join is rejected rather than routed.
Attempting to join a call_id belonging to someone else&apos;s interaction is rejected (manually testable by using a mismatched employee_id).
